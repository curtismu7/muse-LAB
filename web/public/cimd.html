CIMD, step by step: mock and real

With a Client ID Metadata Document the app's client_id is a web address. The authorization server fetches that address, checks what it finds, and only then lets the sign-in go ahead. Below, every request and response, once as a labelled mock of what Muse's connector would do, and once as captured from real servers.

Real Captured on 29 October 2026

The app is client.dev, a public site that hosts an example CIMD document. The authorization server is a local PingFederate 13.1.3 (13.1 is the release that added CIMD). These are the actual responses, trimmed only where marked.

The last step stops at an error, and that is the real result. This PingFederate refused client.dev. PingFederate's documentation says it rejects a CIMD request when no enabled CIMD policy matches, and I have not looked at this server's policies to confirm that is the cause. Getting past it most likely needs a policy for client.dev, which has not been added.

1. The app's document, as anyone can fetch it

Request, no credentials

GET /oauth/metadata.json HTTP/2
Host: client.dev

Response

HTTP/2 200
content-type: application/json; charset=utf-8
access-control-allow-origin: *
cache-control: public, max-age=0, must-revalidate
server: Vercel

{
  "client_id": "https://client.dev/oauth/metadata.json",
  "client_name": "client.dev",
  "client_uri": "https://client.dev",
  "redirect_uris": ["https://client.dev/oauth/callback"],
  "grant_types": ["authorization_code"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "none"
}

The document's own client_id is the address it is served from. That match is the first thing a server checks. token_endpoint_auth_method: none means a public client: no secret, PKCE instead.

2. The server says it understands CIMD

Request

GET /.well-known/oauth-authorization-server HTTP/1.1
Host: local.ping-devops.com:9031

Response (200, five fields kept out of the full document)

{
  "issuer": "https://local.ping-devops.com:9031",
  "authorization_endpoint": "https://local.ping-devops.com:9031/as/authorization.oauth2",
  "token_endpoint": "https://local.ping-devops.com:9031/as/token.oauth2",
  "token_endpoint_auth_methods_supported": ["client_secret_basic", "client_secret_post", "client_secret_jwt",
                                            "private_key_jwt", "tls_client_auth", "none"],
  "client_id_metadata_document_supported": true
}

This is the flag Claude, ChatGPT and Codex look for. With it, and none in the list, they present a document address and never call the registration endpoint (this server also lists /as/clients.oauth2 for DCR).

3. The authorize request, with a web address as the client

Request

GET /as/authorization.oauth2
  ?client_id=https://client.dev/oauth/metadata.json
  &response_type=code
  &redirect_uri=https://client.dev/oauth/callback
  &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
  &code_challenge_method=S256
  &state=x
Host: local.ping-devops.com:9031

Response

HTTP/2 400
content-type: text/html;charset=utf-8

400 - Invalid client_id

PingFederate refused the request before showing a sign-in page. Its documentation says that with CIMD on it reads the client_id as an address, checks its CIMD policies, and rejects the request if none matches. That is the likely cause here, but it is unconfirmed. It fits the design: the server decides which addresses it trusts, and a document anyone can host does not become a client by itself.

Mock What Muse's connector would do

This is scripted, not captured. Muse's connector does not do CIMD yet, so nothing below has been run. The app is client.dev's real document from the other tab, so the shapes match. Codes, tokens and the PKCE values are samples.

2. The app sends the user to authorize

GET /connector/authorize
  ?client_id=https://client.dev/oauth/metadata.json
  &redirect_uri=https://client.dev/oauth/callback
  &response_type=code&scope=mcp
  &code_challenge=SAMPLE_CHALLENGE&code_challenge_method=S256&state=SAMPLE_STATE

Today Muse would answer 400 here, because that client_id is not registered. The new behaviour starts when the client_id is an HTTPS address.

4. Sign-in goes ahead as it does today

With the app accepted, Muse sends the user to PingOne through the DaVinci flow with Protect, the same as for any connector. The user signs in and approves, then Muse redirects to the callback the document listed:

302 Location: https://client.dev/oauth/callback?code=SAMPLE_CODE&state=SAMPLE_STATE

5. The app swaps the code for a token

POST /connector/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=SAMPLE_CODE
&client_id=https://client.dev/oauth/metadata.json
&redirect_uri=https://client.dev/oauth/callback
&code_verifier=SAMPLE_VERIFIER

200 OK
{ "access_token": "SAMPLE_TOKEN", "token_type": "Bearer", "scope": "mcp" }

No client secret anywhere. PKCE proves the app that asked is the app that gets the token, and the document's callback list proves the code went where its owner said.
