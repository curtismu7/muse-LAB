CIMD, step by step: mock and real

With a Client ID Metadata Document the app's client_id is a web address. The authorization server fetches that address, checks what it finds, and only then lets the sign-in go ahead. Below, every request and response, once as a labelled mock of what Personal Agent's connector would do, and once as captured from real servers.

Real ChatGPT, Codex and Claude Code, against Linear and Notion

Captured on 29 October 2026 from the public internet. The apps are the real ones: OpenAI hosts ChatGPT's and Codex's documents, Anthropic hosts Claude Code's. The servers are the real MCP servers of Linear and Notion, both of which advertise CIMD. Nothing here needed an account, because an authorize request only starts a sign-in.

Not captured: what happens after Approve. That needs a signed-in Linear or Notion user, so the code and token steps are not shown on this tab.

Two different kinds of client. Codex and Claude Code are public clients: no secret, PKCE only, a loopback callback with no port written in the document. 2. A real server says it understands CIMD

Request

GET /.well-known/oauth-authorization-server HTTP/2
Host: mcp.linear.app

Response (200, seven fields kept out of the full document)

{
  "issuer": "https://mcp.linear.app",
  "authorization_endpoint": "https://mcp.linear.app/authorize",
  "token_endpoint": "https://mcp.linear.app/token",
  "registration_endpoint": "https://mcp.linear.app/register",
  "code_challenge_methods_supported": ["S256"],
  "token_endpoint_auth_methods_supported": ["client_secret_basic", "client_secret_post", "none"],
  "client_id_metadata_document_supported": true
}

Linear also keeps its registration endpoint, so a client that has no document can still register (DCR). Notion's metadata is the same shape, with private_key_jwt added to the methods it accepts, the one ChatGPT asks for.

Nobody registered ChatGPT with Linear. Linear fetched the document at the client_id address and built its consent page from it: the name in the title, OpenAI's logo from logo_uri, and the website from client_uri. The page is Linear's own, not ChatGPT's.

4. Codex asks, with a callback port nobody listed

The document lists http://127.0.0.1/callback with no port. Linear accepted port 1455 anyway. For a loopback address any port matches, because a command-line app picks a free port when it starts (Codex lets you fix it with mcp_oauth_callback_port). Linear shows the exact callback on its page.

5. A callback the document does not list is refused

Request: the same Codex request, with redirect_uri=https://evil.example/cb

Linear

HTTP/2 400
Invalid redirect URI

Notion

HTTP/2 400

This is what stops anyone from borrowing ChatGPT's or Codex's address: a code is only ever sent to a callback in the document its owner published. Neither server redirected anywhere.

7. Real PingFederate does it too (the CIMD server we use)

Captured on the SE PingFederate on 29 October 2026 (agents-f5, read-only requests plus one owner-approved policy). Host names are replaced with .example names here; the responses are as captured.

PingFederate 13.1 added CIMD. The SE server (pf.example) and a local 13.1.3 both advertise client_id_metadata_document_supported: true and list none and private_key_jwt. Our Personal Agent connector sits in front of PingOne, which has no CIMD, so Personal Agent registers apps by DCR; PingFederate is where CIMD runs.

Before a policy allowed the client: refused. The SE server had CIMD on and three policies, each allowing one exact metadata URL, with PKCE required. client.dev was in none of them, so PingFederate rejects the request:

GET /as/authorization.oauth2?client_id=https://client.dev/oauth/metadata.json&response_type=code&redirect_uri=https://client.dev/oauth/callback&code_challenge=E9Melho...&code_challenge_method=S256&state=x
Host: pf-local.example:9031

HTTP/2 400
400 - Invalid client_id

After one policy for client.dev only (owner-approved; the other three untouched): PingFederate fetches and validates https://client.dev/oauth/metadata.json and sends the client on to its sign-in page, a form titled "Sign in to Ping Identity AI demo" (HTTP 200).

The same with our own hosted document (policy cimdLabOwn, a client document served from our own host): the same result, so PingFederate fetched it from the public internet.

The trap worth knowing. A new access token manager with no authz_req mapping for the sign-in adapter makes PingFederate answer with a redirect to the client and an error. It looks like an authentication-selector problem and is not:

HTTP/2 302
location: https://client.dev/oauth/callback?error=server_error&error_description=There+are+no+authentication+methods+available+for+OAuth.&state=x

Adding the mapping on the token manager is the fix; the default authentication policy was already sending these requests to the sign-in form.

Open Not captured: the authorization code itself, because it needs the demo user's password at the sign-in form. PingFederate acting as a CIMD client is unverified. The Acme PingFederate (pf-acme.example) does not advertise CIMD at all.

Mock What a server does with a CIMD client_id

This is scripted, not captured. It follows what Linear, Notion and PingFederate did on the Real tab, as a plain walk-through of the checks. Personal Agent's own connector does not use CIMD: it sits in front of PingOne, which has none, so it registers apps by DCR. The app is Codex, using its real document from the other tab, so the shapes match. Codes, tokens and the PKCE values are samples. Codex needs only PKCE. ChatGPT's real document asks for private_key_jwt, so supporting ChatGPT would also mean fetching its key set and checking a signed assertion at the token step, which this walk-through does not show.

1. The server advertises CIMD

GET /.well-known/oauth-authorization-server
Host: as.example

200 OK
{
  "issuer": "https://as.example",
  "authorization_endpoint": ".../authorize",
  "token_endpoint": ".../token",
  "code_challenge_methods_supported": ["S256"],
  "token_endpoint_auth_methods_supported": ["none"],
  "client_id_metadata_document_supported": true   <- the one new line
}

2. The app sends the user to authorize

GET /authorize
  ?client_id=https://chatgpt.com/oauth/codex/client.json
  &redirect_uri=http://127.0.0.1:1455/callback
  &response_type=code&scope=mcp
  &code_challenge=SAMPLE_CHALLENGE&code_challenge_method=S256&state=SAMPLE_STATE

A server without CIMD would answer 400 here, because that client_id is not registered. The new behaviour starts when the client_id is an HTTPS address.

3. The server fetches and checks the document

GET /oauth/codex/client.json
Host: chatgpt.com
Accept: application/json

200 OK   (same body as the real capture)

4. Sign-in goes ahead as it does today

With the app accepted, the server shows its sign-in page (on PingFederate, the form from the Real tab). The user signs in and approves, then the server redirects to the callback the document listed:

302 Location: http://127.0.0.1:1455/callback?code=SAMPLE_CODE&state=SAMPLE_STATE

5. The app swaps the code for a token

POST /token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=SAMPLE_CODE
&client_id=https://chatgpt.com/oauth/codex/client.json
&redirect_uri=http://127.0.0.1:1455/callback
&code_verifier=SAMPLE_VERIFIER

200 OK
{ "access_token": "SAMPLE_TOKEN", "token_type": "Bearer", "scope": "mcp" }

No client secret anywhere. PKCE proves the app that asked is the app that gets the token, and the document's callback list proves the code went where its owner said.

What each side does

  • Real ChatGPT, Codex and Claude Code host their own documents. Linear and Notion accept ChatGPT's and Codex's, and refuse a callback that is not in the document.
  • Real PingFederate 13.1.x advertises CIMD. It refused client.dev until a policy allowed it, then fetched and validated the document. The sign-in then failed on a missing token mapping, which is not CIMD.
  • Mock The generic walk-through on the Mock tab. Personal Agent's own connector does not do CIMD by design (PingOne has none); PingFederate does.
  • Open The token step with a real signed-in user, for ChatGPT (private_key_jwt) and Codex. Whether ChatGPT falls back to none when a server lacks private_key_jwt is not verified.

PingFederate's CIMD support follows an evolving draft specification, and its documentation warns later changes may not be backward compatible. See PingFederate CIMD.
