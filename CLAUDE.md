# Personal Agent (Muse)

Personal-agent demo, tier Demo. A browser front end (Muse, the agent) signs in through PingOne, then calls tools through a Privilege-shaped gateway. By default (`MODE=mock`) everything is simulated and offline; `MODE=live` (with `ALLOW_LIVE=1`) is the owner's real build with their own PingOne and gateway. `/clients.html` shows Claude, ChatGPT, Codex and Muse as look-alike clients on the same back end.

## Run and test
- `npm install`
- `npm test` (server suite, node:test; `node --test server/test/*.test.js` also works)
- `npm run build` (web bundle)
- `npm start` (http://127.0.0.1:5100/); `node scripts/doctor.mjs` checks a running app.

## Book a flight (two Authorize rules)
- `server/src/fares.js`: the fare catalogue (`fares.json`, SH101-SH109), the two rules (`RULES`: names and codes match the Authorize policy: `mcp-airline-agent-spend-limit`, `mcp-airline-premium-only`), the Mock member records (`MEMBERS`: standard = Premier Silver, premium = Premier Gold, none = no `airlineMemberTier`; each mimics the PingOne user attribute, the agent limit lives there, default 500) and `evaluateBooking`. Strict "over": exactly 500 and 750 pass. Premium = `PREMIUM_TIERS` (explicit list, `Premier Gold` only; any other value, empty or missing is NOT premium). **The tier is the PingOne user attribute `airlineMemberTier` (owner decision 2026-11-09); in Real, PingOne Authorize reads it itself. The gateway does not look it up or send it, so Real usually shows `member tier not reported to Muse`; never invent a value. Mock labels its tier as a Mock PingOne user mimicking the attribute (`TIER_SOURCE_MOCK`); Real labels it `TIER_SOURCE_REAL`.**
- Mock: `gateway.js fineCheck('flights.book', args, {actor, member})` ignores `args.fare/amount/quoted/tier/limit`; `POST /api/member {member: standard|premium|none}` (and the card's `POST /api/booking/tier`, which also sets the Mock agent limit) sets which Mock PingOne user and limit the simulated Authorize reads (`/api/member` is refused in Real); `booking.js mockBooking` builds the five hops, all labelled simulated.
- Real: `POST /api/live/ask {scenario:'book', flightId, channel:'agent'|'user', quoted?}`; `booking.js classifyBooking` reads the gateway's answer (403 + `X-Gw-Audit-Trail` statements, 428 consent, 200 booked or not_booked, anything else an error). A direct-user token is kept in `ws.userToken` on the server only. Only tested against stubs.
- Connector (muse.ai): `connector.js toolsFor` lists `loyalty_balance`, `get_loyalty_status`, `list_flights`, `book_flight` (also on `/mcp-pf`, where `book_flight` books nothing: no gateway there). `book_flight {flightId}` validates against the catalogue, sends only `{flight_number}` to the gateway tool (`bookingTool(env)`), reads the answer with `classifyBooking`, and `bookingToolResult` turns it into the MCP result: booked only for 200 + `booked:true`, denials name the rule from `X-Gw-Audit-Trail` codes, 428 is held, nothing echoes tokens/headers/bodies. The sent booking call is never retried. `no_user_consent` / `may_act_mismatch` statement codes give the plain "you have not authorized this agent to act for you on bookings" message (plus a bridge-not-configured note when there is no secret). Tests: `server/test/connector-booking.test.js`, `server/test/connector-consent-bridge.test.js`.

## Consent bridge (exception #2, owner-approved 2026-11-09)
- `MUSE_GATEWAY_INTERNAL_SECRET` (name only here and in `.env.example`, commented; compose passes `${MUSE_GATEWAY_INTERNAL_SECRET:-}`) holds the gateway's trusted-caller secret in Muse's own `.env`. DEVIATION from the rulebook, for this one purpose only.
- `connector.js bookFlight` passes `{ 'x-internal-gateway-secret', 'X-May-Act-Sub': session.actor }` to `liveauth.js callGateway(..., { extraHeaders })`, which puts them on the `tools/call` request alone (not initialize or tools/list). `session.actor` is the configured client id of the PingOne app the session signed in with (stored at sign-in), never a request field. Only the book_flight path; no other trusted header; no secret means no extra headers.
- The secret is write-only: it lives in the `mountConnector` closure, never in `cfg`, a session, a step, a log (log lines that could echo it go through `redact`), an error or a result. Only a plain header value is accepted. Never put it in a file in the repo; agents test with stubs and invented secrets only.
- UI: `web/src/BookFlight.jsx`; diagram `booking-rules-flow` (also a tab on /diagram).
- Never call a real tenant or the real gateway from tests or agents; Real is owner-run.

## Test controls: member tier + agent limit (owner-approved 2026-11-09, opt-in)
- `server/src/tier.js` + `/api/booking/tier` (GET state, POST `{member?: standard|premium|none, limit?: <whole dollars 1..100000>|"default"}`, either or both, unknown fields ignored) + `/api/booking/tier/read` (Real read-only) + the *Test controls* card (`TierCard` in `web/src/BookFlight.jsx`; pure helpers in `web/src/bookingExpect.js`). Mock: sets `ws.member` (the Mock PingOne user) and `ws.agentLimit` (null = default 500; `fares.js mockMember`, used by `gateway.js`/`booking.js`); Reset, sign-out and a mode switch clear both. Real: ONE PATCH per `MUSE_TIER_USER_IDS` user with exactly the changed attributes (`airlineMemberTier`, `agentSpendLimit` as a STRING like `"500"`; clear = `null`), worker token by client credentials (Basic auth), each user read back, `verified` only if every sent field matches. Tests: `server/test/tier.test.js`, `server/test/booking-rules.test.js` (stub PingOne only), `web/src/test/{bookingExpect,testcontrols}.test.js*`.
- `readUserFacts(userId)` on the switch returns `{tier, limit}` (limit a number or null) for allow-listed ids only, else `{tier: null, limit: null}` (also on any error). Not wired into the connector.
- **This is a DEVIATION from the rulebook, labelled owner-approved 2026-11-09, and the opt-in flag is required:** a runtime PingOne credential (`MUSE_TIER_ENABLE=1`, `MUSE_TIER_WORKER_CLIENT_ID`, `MUSE_TIER_WORKER_CLIENT_SECRET`, `MUSE_TIER_USER_IDS`, `MUSE_TIER_ENV_ID`, `MUSE_TIER_REGION`; names only here) for this feature only. The Docker container always has `MUSE_HOSTED=1`, so `MUSE_TIER_ENABLE` is what turns the controls on there; `MUSE_HOSTED=1` without it refuses (the SE deployment never sets it). Keep it narrow: two attributes, tier values Gold/Silver/clear and a whole-dollar limit 1..100000 or clear, allow-listed ids from env never from a request, hosts `auth.pingone.<region>` / `api.pingone.<region>` only, secret and token never returned, logged, scrubbed from errors, Real only. Do not widen it, do not reuse `provisioning.json`, never read or print `.env`.
- Agents never call a real tenant for this: test only against the stub in `tier.test.js`. Clearing with `null`, the worker app's required role and the `agentSpendLimit` schema attribute's behaviour in Authorize are UNVERIFIED against a real tenant by agents.

## Rules that bite
- Mock mode contacts nothing: the netguard (`server/src/netguard.js`) refuses every non-loopback outbound call and counts them (`GET /api/netguard`; the doctor and a test assert zero attempts). In live mode it only counts origins.
- Branding is data: `server/src/customer.config.json` (brandName, agentName, tagline, default vertical); `MUSE_CUSTOMER_CONFIG` points at another file. Bad values fall back to the defaults.
- Stories are data: `server/src/stories.json`, three vertical packs (airline, bank, hotel) with `{{cast.x}}` tokens and the runtime tokens `{{points}}` and `{{tier}}`. An undefined token fails the load and the tests. Live sign-in runs the airline back end only.
- Each browser gets its own workspace; `workspaceId` (a hash, never the cookie) labels it. Nothing is written to disk.
- Loopback bind unless `MUSE_HOSTED=1`. Host check and same-origin writes on every API call.
- Persona picker only with `IDP=mock` and `ALLOW_MOCK_SIGNIN=1`, never hosted.
- No SE host names, tenant or client ids in shipped files (a test pins it). Real settings live in `.env` (see `.env.example`) or the owner's Secret, never in the repo.
- Live sign-in is pi.flow, not a redirect: the page opens the Sign in dialog (`web/src/SignInModal.jsx`), which runs PingOne's DaVinci flow with Ping's DaVinci client SDK (`@forgerock/davinci-client`, plus `@forgerock/protect` for the Protect screen). `POST /api/live/signin` with `piflow: true` returns the SDK's config (state, challenge, hint; never the verifier) and `POST /api/live/signin/complete` swaps the code on the server. The PingOne app must list the page's origin in its CORS settings (without it the browser blocks the flow). The connector's `/connector/authorize` (real assistants and the simulated ones from `/api/sim/start` and `clients.html`) sends the browser to Personal Agent's own `/connector/signin` page, which runs the same dialog (`/connector/signin/config`, `/connector/signin/complete`); the only redirect left is back to the assistant's own redirect address. Each PingOne app a sign-in uses (the base app and the per-assistant apps) needs the page's origin in its CORS settings and `<public url>/connector/callback` in its redirect URIs. Without a PingOne app (`MUSE_P1_ENV_ID`, `MUSE_P1_CLIENT_ID`) Real mode refuses to register or sign in (409); there is no redirect fallback and no dynamic client registration against the gateway's own authorization server.
